# Открытие формы и подтверждённые заявки

## Открытие формы записи

После появления общей формы записи в DOM сайт отправляет отдельное событие:

```js
{ event: "booking_form_open", form_type: "appointment" }
```

Оно срабатывает один раз на открытие: из кнопки на странице услуги, карточки врача, калькулятора или по прямой ссылке `/contacts#booking`. Ввод данных, загрузка списка услуг и повторные рендеры не создают дублей. Закрытие и повторное открытие считаются новым открытием. На странице с закрытой формой события нет. Это событие общей записи, а не открытия обратного звонка или декларации.

Имя, телефон, врач, процедура, адрес, содержимое полей и параметры URL в событие не передаются. Внутренний маркер открытия используется только для дедупликации в памяти.

Чтобы видеть открытия в GA4, в GTM нужно добавить триггер **«Пользовательское событие»** с точным именем `booking_form_open` и тег события GA4 с тем же именем. Передавать `form_type` из переменной уровня данных; запуск — один раз на событие. Сайт сам помещает событие в `dataLayer`, дополнительный обработчик клика или показа формы в GTM не нужен. Настройки контейнера меняются отдельно от кода сайта.

Для воронки сравнивать `booking_form_open` с подтверждённой отправкой, в обоих случаях с `form_type = appointment`. Открытие формы не является заявкой и не должно запускать существующий тег конверсии отправки. Для количества людей использовать пользователей в отчёте, для количества открытий — число событий; повторные открытия одного человека возможны.

## Подтверждение заявки

Сайт отправляет в window.dataLayer событие `form_submit` только после успешного ответа `/api/bookings` с непустым номером сохранённой заявки и появления блока подтверждения в DOM. Пользователь на этом этапе видит благодарность либо «Заявку прийнято».

```js
{ event: "form_submit", form_type: "appointment" }
```

Значения `form_type`: `appointment` — общая запись, включая врача, исследование и выезд медсестры; `callback` — обратный звонок; `family_declaration` — декларация. Имя, телефон, дата рождения, комментарий, врач, исследование и номер заявки в событие не входят. Номер используется только для дедупликации в памяти текущего документа.

## Запуск отправки

Кнопка сохраняет `type="submit"` для стандартной активации клавишей Enter. Обработчик кнопки синхронно отменяет действие браузера, проверяет поля через `reportValidity()` и вызывает async-обработчик напрямую. Нажатия кнопки и Enter не создают ранний DOM `submit`, который Google мог бы принять за полученную заявку. Нативные ограничения required/pattern, существующие сообщения об ошибках и серверная проверка сохранены.

Не вызывать `requestSubmit()`, `form.submit()` или искусственный DOM `submit`: они обходят обработчик кнопки. Защитный `onSubmit` отменяет навигацию, но не используется для отправки заявки.

События нет при неверных/неполных данных, ожидании ответа, ошибке сервера/сети, ответе без номера заявки и срабатывании скрытого антиспам-поля. Повторный рендер подтверждения и повторная обработка того же номера не создают дубль. Ошибка сторонней аналитики не превращает успешно сохранённую заявку в ошибку формы.

## Совместимость с GTM

Проверенный 12.10.2026 публичный контейнер `GTM-KB6VQTKM`, версия ресурса 21: Ads tag_id 38 запускается по точному событию `form_submit` без дополнительных условий по полям. Его настройка — один раз на событие. Подтверждённое событие сайта подходит существующему триггеру. Триггера `booking_form_open` в этой версии пока нет.

Прежнее событие сайта `booking_success` больше не отправляется: одновременная отправка обоих имён запускала бы два разных тега Ads (38 и 25). Теги и история старого события автоматически не удаляются.

GA4 tag_id 36 в этой версии контейнера преобразует `form_submit` в `form_submit|GTM` и уже настроен «один раз на событие». Поэтому в текущем отчёте GA4 завершение воронки нужно выбирать как `form_submit|GTM`, а триггер на стороне сайта/GTM остаётся `form_submit`. Имя и частота этого GA4-тега задаются в GTM, не в коде сайта. Перед настройкой повторно проверить актуальную версию контейнера.

Клики `online_booking_click` и начало заполнения `form_start` — самостоятельные ранние действия, а не подтверждённые заявки. Их теги, цели кампаний и статус основных/вторичных конверсий задаются в GTM/Ads. Не учитывать одну заявку одновременно через прямой тег Ads и импорт той же заявки из GA4. Отдельные цели звонков проверять отдельно.

## Проверка

1. Все три формы, неполный телефон, кнопка и Enter: нет запроса заявки, нативного submit и form_submit.
2. Полные данные, задержанный ответ: один запрос, повторная отправка заблокирована, события ещё нет.
3. Отказ сервера/сети: видна ошибка, события нет, повторная попытка доступна.
4. Подтверждённый номер: блок благодарности уже в DOM при ровно одном form_submit; booking_success отсутствует.
5. Новое открытие и новая успешная заявка создают новое событие; рендер прежнего подтверждения — нет.
6. После публикации проверить существующий триггер на текущем сайте. Успешные сценарии выполнять в изолированном окружении либо с согласованной реальной тестовой заявкой.

Публичная CSP разрешает региональные запросы Analytics (`*.analytics.google.com`), существующие запросы Ads и загрузку скриптов с точного хоста `https://googleads.g.doubleclick.net`. Последний разрешён в `script-src`; при отсутствии отдельной директивы `script-src-elem` браузер использует это же правило для элементов `<script>`. Это устраняет блокировку из диагностики Google. Админка и API не подключают аналитику. Изменение CSP начинает действовать после публикации сайта.

## Рабочий проект Microsoft Clarity

13.10.2026 владелец подтвердил проект специалистов: **`xh4cq19oo9`**. Публичный GTM содержит также старый проект `yt2f9sy2qc`; одновременная загрузка двух конфигураций Clarity делает выбор проекта зависимым от порядка исполнения.

На стороне сайта `script-src` разрешает только точный URL `https://www.clarity.ms/tag/xh4cq19oo9` и SDK с `https://scripts.clarity.ms`. Параметр `?ref=gtm` допустим, другой ID — нет. Коллекторы и пиксели Clarity сохраняют разрешения по доменам; админка и API остаются без аналитики. Отдельный скрипт Clarity в разметку не добавлен.

Это отключение загрузки старого проекта на сайте, а не удаление тега из GTM. Пока владелец контейнера не приостановит или не удалит tag_id 41 (`yt2f9sy2qc`), в консоли ожидаема его CSP-блокировка. Шаблон GTM может по-прежнему ставить команды `identify` в общую очередь Clarity до заблокированной загрузки; полное удаление этого шаблона требует доступа к GTM. Рабочий tag_id 40 (`xh4cq19oo9`) нужно сохранить.

В изолированной браузерной проверке с текущим CSP оба порядка загрузки тегов и настоящий контейнер GTM выбирают `xh4cq19oo9`; сервер Clarity принимает `/collect` с HTTP 204. Это подтверждает сетевую доставку, но не просмотр записи в панели Clarity. При изменении проекта нужно одновременно обновить разрешённый URL и тесты в `tests/proxy-security.test.mjs`. [Документация Clarity по CSP](https://learn.microsoft.com/en-us/clarity/setup-and-installation/clarity-csp).

Предупреждение Google «Обнаружены дополнительные домены» относится к настройкам Google-тега. Нужно открыть список обнаруженных доменов и сверить его с фактическими доменами центра; добавлять все найденные адреса автоматически не следует. Это предупреждение не устраняется изменением CSP.

Событие подтверждает сохранение заявки, но не доставку email, дозвон или согласование приёма. Блокировщик аналитики может препятствовать отправке в Google, не влияя на форму.

Официальные источники: [dataLayer](https://developers.google.com/tag-platform/tag-manager/datalayer), [основные и вторичные конверсии](https://support.google.com/google-ads/answer/11461796?hl=ru), [CSP для Google tags](https://developers.google.com/tag-platform/security/guides/csp), [Enter и неявная отправка](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#implicit-submission).
